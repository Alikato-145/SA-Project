# ข้อเสนอการเลือกประเภทรับเงินและสรุปยอดจ่ายตามสาขา

## ความต้องการที่ผู้ใช้ยืนยัน

พนักงานเลือกประเภทรับเงินได้สามแบบ: เงินสด เงินโอน และประกันสังคม ผ่านหน้าตั้งค่า/ข้อมูลส่วนตัว โดย HR กำหนดแทนได้ หน้าเตรียมจ่ายแสดงจำนวนพนักงานและยอดเงินเดือนสุทธิที่ต้องจ่ายแยกตามสาขาและทั้งสามประเภท ประเภทประกันสังคมจ่ายเงินสุทธิเข้าบัญชีธนาคารพนักงาน ยอดประเภทประกันสังคมในตารางนี้คือยอดเงินเดือนที่จ่ายให้กลุ่มนั้น ไม่ใช่ยอดเงินสมทบประกันสังคม การโอนเงินจริงดำเนินการภายนอกระบบ

## ความต่างจาก schema ปัจจุบัน

`employees.payment_method` และ `payroll_payments.payment_method` ใช้ PostgreSQL enum ที่มี `cash` และ `transfer` เท่านั้น กลุ่ม `social_security` ปัจจุบันอนุมานจาก `payroll_records.is_social_security_member_snapshot` โดยพนักงานไม่ได้เลือกกลุ่มเอง Trigger `enforce_payroll_payment_snapshot` กำหนดปลายทางบัญชีหรือ PromptPay ตามสถานะสมาชิกที่ล็อกไว้ ข้อมูลการเตรียมจ่ายเป็น immutable snapshot จึงใช้การเปลี่ยนสถานะสมาชิกหรือเบอร์โทรมาแอบแทนตัวเลือกใหม่ไม่ได้

## ขอบเขตที่ต้องประสานเจ้าของ schema

เสนอเพิ่มฟิลด์ประเภทจ่ายที่พนักงานเลือก (`cash`, `transfer`, `social_security`) และ snapshot ที่รายการเตรียมจ่าย พร้อม migration, constraint และ trigger รองรับการโอนธนาคารสำหรับกลุ่มประกันสังคม ต้องออกแบบค่าเริ่มต้น/การแปลงข้อมูลเดิมอย่างระมัดระวัง รักษากลุ่มและปลายทางของรายการที่เตรียมหรือจ่ายแล้วตามข้อมูลเดิม และไม่แก้ประวัติแบบเงียบ ระบบยังต้องใช้สถานะสมาชิกจริงแยกจากประเภทที่เลือกเพื่อคำนวณเงินสมทบตามกฎเดิม

บริการต้องจำกัด self-service ให้แก้เฉพาะพนักงานของตนและ HR/เจ้าของแก้แทนตามสิทธิ์ บันทึก audit โดยไม่บันทึกเลขบัญชีเต็ม ภาพสรุปแยกสาขาคิดเป็นเงินสตางค์แบบ exact รวมเงินสด/โอน/ประกันสังคมทุกกลุ่ม (รวมสมาชิกที่เลือกเงินสดหรือโอนได้) และใช้ snapshot ของรายการที่เตรียมแล้ว ตรวจจำนวนและยอดรวมตรงยอดสุทธิรวม โดยต้องแยกยอดพร้อมจ่ายกับจ่ายแล้วให้ชัด

## หลักฐานทดสอบที่ต้องมี

ทดสอบการเลือกทั้งสามแบบและสิทธิ์ของพนักงานตนเอง/ผู้อื่น/HR, โอน PromptPay, แบบประกันสังคมที่ไม่มีหรือมีบัญชีหลัก, สรุปหลายสาขาและยอดเศษสตางค์, การเปลี่ยนค่าหลังเตรียมจ่าย, การยกเลิกและเตรียมใหม่ และข้อมูลเดิมหลัง migration; ทดสอบเฉพาะ PostgreSQL และ browser บน disposable stack ไม่โอนเงินจริง

AGENTS.md ระบุ schema และ migration frozen ระหว่าง sprint และให้รายงานความต่างแก่ schema owner ก่อนเปลี่ยน จึงต้องประสานเรื่องการปลด freeze และ migration ก่อนลงมือแก้ schema หรือ trigger

## การอนุญาต

วันที่ 30 ตุลาคม 2026 ผู้ใช้ยืนยันว่าเป็นผู้ดูแล schema และอนุญาตปลดข้อจำกัดเฉพาะการเปลี่ยนแปลงสำหรับงานนี้ การทดสอบ migration ทำบนฐาน verification เท่านั้น; การนำ migration ไปใช้กับฐานจริงยังเป็นขั้นตอนแยกและยังไม่ได้ดำเนินการ
